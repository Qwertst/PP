## 1. Пререквизиты

| | значение |
|---|---|
| Процессор | Intel Xeon Gold 6230 @ 2.10 GHz, 12 ядер доступно |
| ОС / ядро | Ubuntu 22.04, Linux 5.15.0-143-generic |
| Компилятор | g++ 11.4.0, `-O2 -std=c++20 -pthread` |

Сортируем `vector<int>` со случайными значениями (seed фиксирован). Перед каждым из `reps` прогонов копируем исходный массив (копирование вне замера), замеряем только саму сортировку, проверяем `is_sorted`.

## 2. Алгоритм

Классический merge sort с одним общим буфером `tmp` на `N` элементов:
- `mergeSortSeq` - рекурсивно сортирует половины и сливает их.
- `mergeSortPar` - то же, но левую половину считает отдельный `std::thread`, правую текущий поток; после `join` идёт слияние. Параллелизм ограничен двумя параметрами: `depth` и порогом `cutoff` (аргумент, по умолчанию 32768): куски меньше порога сортируются в одном потоке.

Само слияние `merge` всегда последовательное - распараллеливается только дерево рекурсии.

Пусть `T` - число потоков. На глубине рекурсии `depth` получается до `2^depth` потоков. Чтобы листьев было примерно `T`, берём `depth = ceil(log2(T))`.

Масштабирование по числу потоков, N = 10 000 000:

N от ~5*10^4(выше базового `kCutoff`): параллельная стабильно быстрее, выигрыш растёт с размером и выходит на плато ~5-6x на 12 ядрах. Быстрее многопоточная.

## 4. Влияние порога cutoff

`cutoff` задаёт минимальный размер куска, который ещё дробится на потоки. Число реально создаваемых потоков и размер последовательного куска зависят от него.

При `T = 12` глубина `depth = log2(12) = 4` сама ограничивает число листьев 16-ю, поэтому `cutoff` почти не виден на большом диапазоне и портит только на больших значениях (когда кусок перестаёт дробиться раньше, чем набирается 16 потоков):

| cutoff | мс/проход (T=12) |
|---|---|
| 1 024 | 266.7 |
| 16 384 | 265.6 |
| 65 536 | 264.5 |
| 262 144 | 263.6 |
| 1 048 576 | 253.6 |
| 4 194 304 | 433.9 |

Если снять ограничение по `depth` - тогда число потоков определяется только порогом. Получается U-образная зависимость, N = 10 000 000:

| cutoff | мс/проход (T=4096) | что происходит |
|---|---|---|
| 256 | 494.6 | тысячи `std::thread`, накладные расходы съедают выигрыш |
| 1 024 | 459.8 | то же |
| 4 096 | 457.0 | то же |
| 16 384 | 307.6 | потоков всё ещё слишком много |
| 65 536 | 276.3 | приближаемся к оптимуму |
| 262 144 | 266.3 | оптимум |
| **1 048 576** | **264.9** | **оптимум** |
| 4 194 304 | 441.4 | кусков мало (~4), ядра простаивают |

Слишком маленький `cutoff` - слишком много потоков, побеждают накладные расходы на их создание и планирование; слишком большой - мало независимых кусков, ядра недозагружены. Оптимум широкий, порядка `10^5...10^6` элементов на кусок (примерно `N / число_ядер`).

## 5. Выводы

- На малых данных (< ~30k элементов) распараллеливание не окупается - быстрее (или столько же) однопоточная версия.
- На больших данных многопоточная версия выигрывает и выходит на ~5-6x при 12 потоках; дальше упирается в последовательное слияние и память.

## 6. Воспроизведение

```bash
make
make run # seq vs par (T=12) по сетке N
make scale  N=10000000 # par при T = 1,2,4,8,12
make cutoff N=10000000 # par при разных cutoff (T=12)
```

Либо руками:
```bash
./mergesort N mode [reps] [threads] [cutoff]
# mode: seq | par
```
